# Decision log

| Date | Decision | Why | Alternatives considered |
| --- | --- | --- | --- |
| 2026-11-12 | One Postgres schema per layer: `meta`, `bronze`, `silver`, `gold` | Simple; visible in any SQL client; grants can be set per layer | Separate databases (cross-layer queries need dblink/FDW); table name prefixes (no permission boundary, noisy) |
| 2026-11-12 | Idempotent migration runner (`pipeline/migrate.py`) re-applies every `db/sql/*.sql` in order; each file must be idempotent | `docker-entrypoint-initdb.d` only runs on a fresh volume, and this DB already exists | initdb scripts; Alembic (version table + revision files is more machinery than a handful of `IF NOT EXISTS` files needs) |
| 2026-11-12 | Plain psycopg 3 + SQL, no ORM | The pipeline is SQL-centric (bulk loads, `INSERT ... SELECT`); an ORM adds a layer without benefit. Replaced the earlier SQLAlchemy/Alembic scaffold | SQLAlchemy Core/ORM |
| 2026-11-12 | Pipeline core separated from API/UI; CLI first | The assessment requires a runnable script; an API/UI is a thin layer on top of the same functions | API-first service; notebooks |
| 2026-11-12 | Bronze stores each record as `raw_line` (exact text) + `payload` JSONB of raw strings | Works for any CSV without DDL per file; nothing is lost, even for rows that don't parse | One typed column per CSV column (needs a schema up front, a bad value fails the row); all-text columns per file (dynamic DDL, still loses unparseable rows) |
| 2026-11-12 | `row_hash` = sha256 of `raw_line`, computed once when the row is built, before batching | Stable across runs, batch sizes and fallback paths, so identical records always share a hash | Hash of the parsed payload (depends on header normalization); including run/batch/line in the hash (never matches across runs) |
| 2026-11-12 | Idempotency keyed on the file's sha256, not on `row_hash` | Re-running the same file is a no-op, while legitimately repeated rows inside a file are kept (dedup is silver's job) | Unique `row_hash` (silently drops real duplicates); keyed on file name (a changed file with the same name would be skipped) |
| 2026-11-12 | Python `csv` module, not pandas | Exact control: raw text kept per record, the true starting line, nothing coerced; pandas can skip bad lines, infer types and turn "NA"/"" into NaN | pandas `read_csv`; Postgres `COPY ... CSV` straight into a table (one bad row aborts the load) |
| 2026-11-12 | The run row is written in its own committed transaction before loading starts | A crashed or failed load still leaves a `failed` run with its error | Writing the run row inside the load transaction (a rollback would erase the evidence) |
| 2026-11-12 | One transaction per run, with a savepoint per batch (not a commit per batch) | The run is atomic (all rows or none, so a retry is clean), and one bad batch doesn't abort the run | Commit per batch (partial loads to clean up; noted under Scaling for very large files) |
| 2026-11-12 | COPY per batch, falling back to row-by-row INSERTs only for a batch whose COPY fails | COPY is fast in the normal case; the fallback isolates the exact failing row(s) | Always row-by-row (slow); COPY only (one bad row loses the batch) |
| 2026-11-12 | `bronze.load_errors` keeps rows the database refused (raw text, hash, DB error) | Keeps "no data loss" true even when Postgres rejects a row | Logging rejected rows only (not queryable; lost with the log) |
| 2026-11-12 | Reconciliation funnel: ok + malformed + load_failed must equal records parsed, both in memory and in the DB, or the run fails | Proof, per run, that every record is accounted for | Trusting row counts from COPY |
| 2026-11-12 | The profiler computes facts in code; an LLM only interprets them later | Counts, shares and formats must be exact and reproducible; an LLM is good at judging what facts mean, not at counting 10k rows | Letting the agent read raw rows (costly, not reproducible, misses rare cases) |
| 2026-11-12 | Profile only the run's `parse_status = 'ok'` rows; malformed rows are summarised from the run funnel | Malformed rows have shifted or missing fields, so they would distort per-column statistics | Profiling every row (misaligned values pollute stats) |
| 2026-11-12 | Pattern masks (letter runs → `A`, digits → `9`) as the generic format detector; explicit regex + strptime list for dates | Works on any column without knowing its meaning; unknown formats show up as masks and as `unparsed`, not as silent guesses | `dateutil`/pandas date inference (guesses day/month order silently, new dependency) |
| 2026-11-12 | Compact profile (≤ 2 KB per column; example lists trimmed to fit) | LLM cost and context grow with the number of columns, not rows; 13 columns ≈ 18 KB | Full value distributions per column |
| 2026-11-12 | Samples drawn with a fixed seed derived from run_id + column | Profiling the same run twice gives byte-identical JSON, so agent outputs are reproducible and diffable | Unseeded random samples; first-N rows (biased to the top of the file) |
| 2026-11-12 | Custom profiler instead of ydata-profiling | JSON shaped for the agent, small and fast; targeted checks (null-like tokens, day/month evidence, numbers in text, key repeats, date order) | ydata-profiling / great_expectations (heavy, HTML-oriented, generic stats we would have to re-map) |
| 2026-11-12 | Profiler conventions: type shares are nested (float ⊇ integer, datetime ⊇ date); role checks run constant → free_text → candidate_key → categorical; ambiguous DD/MM vs MM/DD follows the majority evidence per format; date columns are never treated as keys | Avoids false "mixed" types for int+float or date+datetime columns, unique sentences labelled as keys, and timestamps flagged as repeating keys | Flat type shares; the spec's rule order as written (both produced misleading flags on real data or fixtures) |
| 2026-11-13 | Profiler v1.1: every threshold and token list in one frozen `PROFILE_CONFIG` (`pipeline/profile_config.py`); the full config, `profiler_version` and a 12-char config hash are written into each dataset summary | Rules are tunable in one place, and two profiles are only comparable when their config hashes match | Constants scattered across modules (v1.0); env-var overrides (more surface than a take-home needs) |
| 2026-11-13 | Sentinel detection: known placeholder dates (1900-01-01, 0000-00-00, 9999-12-31, …) and numbers (-1, 999, -999, …; 0 only when it spikes) plus a generic spike rule (share ≥ 5% and ≥ 10× the median frequency, in non-label-like columns with ≥ 20 distinct values, max 2 spiking values). Numeric stats are reported both with and without suspected sentinels; OUTLIERS and date range facts use the values without them | Sentinels distort mean/IQR (sla_hours mean 104 with 999s, 29 without) and would double-report as outliers or future dates. The max-2 rule keeps templated columns (4 canned resolution notes) from being called "placeholders" | Flag sentinels via IQR only (a 7% spike widens the IQR and hides itself); drop sentinels silently (that is a cleaning decision) |
| 2026-11-13 | Normalization key (accents stripped, lowercased, separators removed; letterless values only lower+strip) groups spelling variants; typo neighbours (difflib ratio ≥ 0.85, or one adjacent letter swap) are reported for label-like columns. Both are **candidates**: the agent decides mappings, the profiler only suggests | Deterministic code is good at "these strings are near each other", bad at meaning (Exterminator vs Pest Control has no string similarity). Plain one-edit distance was rejected after it paired "test" with "Pest" | Auto-apply mappings in the profiler; Levenshtein ≤ 1 (too loose for 4-letter words); embeddings (needs a model/dependency) |
| 2026-11-13 | Functional-consistency checks (one key → several values of another column) deferred to an agent drill-down tool | n×(n−1) column pairs is noisy and mostly meaningless without knowing which columns are keys; the agent can ask for specific pairs it suspects | Profile every column pair up front |
| 2026-11-13 | Streaming sketches (HyperLogLog for distinct counts, Misra-Gries / count-min for top values, t-digest for quantiles) deferred to the 100× path | At 10k rows exact counts take ~1 s; sketches add dependencies and approximation without benefit at this size | Use sketches now |
| 2026-11-13 | Business context: human-written first (`--context-file`, approved on entry, no LLM call); otherwise ONE cheap-model call (Claude Haiku 5.5, effort low) drafts it from column names, role hints, types, row count and 3 sample rows (60-char values, PII-hinted columns masked to their pattern). Drafts are stored `inferred`, unapproved, until `context --approve`; the card marks them UNAPPROVED | Domain knowledge beats inference and costs nothing; a draft is cheap (~fractions of a cent) but can be wrong, so it never silently becomes truth. Column names are JSON-schema enums so the model can't invent columns; pydantic validation drops any that slip through and records them | Always infer with the main model (cost, and still unverified); no context at all (agent loses the "what is this data for" frame) |
| 2026-11-13 | Thin LLM client (`pipeline/llm.py`, one function) with a response cache and three modes: replay (cache only, no key or network), live (cache-first), record (always call, overwrite). Every call incl. cache hits and failures goes to `meta.llm_calls` with tokens, cost and latency; a cache hit costs $0 but keeps the original usage | Reviewers can rerun the whole pipeline without an API key; costs are auditable per run; transient errors are retried by the SDK (2 retries, backoff), so no extra retry layer | LangChain/LiteLLM (abstraction layers we don't need); no cache (non-reproducible, every rerun costs money) |
| 2026-11-13 | No `temperature=0`: the current API rejects sampling parameters (and SDK 2.x has no such argument). Reproducibility comes from caching the exact response by request hash and replaying it | Same input → same stored answer, which is stronger than temperature 0 (which is not deterministic anyway) | Pin an older API version just to send temperature |
| 2026-11-13 | The dataset card is an index, not a dump: the agent reads it every turn, details stay behind tools (`get_column_profile`, `list_issues`). Rendered by pure Python (0 LLM tokens), deterministic, stored with its hash and metrics | The full profile is ~7.5k tokens for 13 columns and grows linearly with columns; the card is ~1.3k tokens here and stays within a fixed budget for 150 columns | Send the full profile every turn; let an LLM summarise the profile (costly, non-deterministic, can drop issues) |
| 2026-11-13 | Tiered budget with compression and a coverage guarantee: Tier 0 (context, header, all high issues, critical columns) is never dropped; later tiers show as many lines as fit and one pointer line counts the rest; room for every later pointer is reserved first. Over-budget Tier 0 renders anyway with a WARNING and `over_budget` | Every column and issue is either visible or counted with the tool call that reveals it, so the agent can't be blind to a problem it was never told about | Drop lowest tiers (silent omission); truncate text at the budget (cuts mid-section) |
| 2026-11-13 | Card cost multiplies by agent turns, so the card goes first in the prompt and is byte-stable (no timestamps, sorted content) to hit the provider prompt cache | A 20-turn agent session re-reads the card 20 times; cached reads cost 5–10% of input price | Re-render per turn; put volatile text before the card |
| 2026-11-13 | Day/month order: per date format, ambiguous values (both parts ≤ 12) follow the majority of that format's unambiguous values in the same column (a part > 12 proves the order); month-first on a tie. Kept as is in v1.2 after an investigation of DATE_ORDER on raw_tickets: rows with no day/month format on either side (ISO, month names, epoch) violate at 34.7%, the unambiguous-only rate is 35.3% (overall 35.1%), both columns show only month-first evidence (0 day-first values), and flipping every ambiguous value raises the rate (34.4% → 38.2%). DATE_ORDER evidence now carries the format-pair breakdown and the unambiguous-only share so this check is repeatable | The order follows evidence in the data, not a locale guess; the evidence-rich DATE_ORDER lets the agent tell parsing artefacts from real data problems | A global locale setting (wrong for mixed sources); a dataset-wide shared vote (not needed here: both columns agree; revisit if a dataset shows conflicting columns) |
| 2026-11-13 | Duplicate classification: exact = same raw line hash; near = same row under the normalization key (case, accents, separators, all missing forms equal). Both counts, their example source lines, and every key-like column checked are always in the summary, even at 0. Key repeat groups get a hint: `exact_duplicate` (nothing else differs after normalization), `update_history` (only time-like or status-like columns differ: date/datetime type, a context tag timestamp/status, or a categorical column with ≤ 10 values), `conflicting` (anything else differs); KEY_WITH_REPEATS severity follows the worst hint (high / medium / low) | "0 duplicates" must be distinguishable from "not checked"; and a repeated id means different things (re-sent row, ticket history, id collision) that need different silver rules — the hint lets the agent choose without reading rows | Report repeats without classification (agent has to drill into every group); name-based rules (`status`, `updated_at`) — not generic |
| 2026-11-13 | Numbers in text are classified by kind (currency prefix/suffix, percent, thousands separator, European decimal, parentheses negative, unit suffix, scientific) with `numeric_after_cleanup` = share of values that would be numbers after stripping those; `zero_share` is reported as a fact on every numeric column, not an issue | The agent can judge whether one numeric cleaning rule is viable (cost: 99.8%) and whether 0 is a placeholder, instead of guessing from 3 examples | Flag every zero (0 is often legitimate); fix formats in the profiler (cleaning is silver's job) |
| 2026-11-13 | Card tokens: estimate = ceil(chars / 2) (configurable); with `card --exact` the provider count drives the budget (re-render with the measured chars/token while over budget, ≤ 3 tries) and both numbers plus `chars_per_token` are stored | chars/4 undercounted the card ~2× (measured 1.94, then 1.79 chars/token after compaction): dense numbers, identifiers and punctuation | tiktoken-style local tokenizers (wrong tokenizer for Claude); always counting exactly (needs a key; replay must work offline) |
| 2026-11-13 | Card compaction (3,498 → 2,356 exact tokens, nothing dropped): evidence ≤ 80 chars with short keys (n, sh, of, ex), `value×count` pairs, unquoted simple strings, short issue codes and tag codes, `@conf` only below 100%, config hash instead of config, critical columns only in their own section. Each change was measured with the token-count endpoint before keeping it (short issue codes alone: −229 tokens) | The card is re-read on every agent turn; tokens, not characters, are the cost | Drop low-severity issues (breaks the coverage guarantee); summarise with an LLM |
| 2026-11-13 | Data minimization in one module (`pipeline/privacy.py`) for every LLM input — context prompt, card, later agent tools. Raw values only for label-like, non-sensitive columns (categorical/constant role, boolean-like, or ≤ 5% distinct); everything else is shown as a pattern (`<A A>`, `<9999-99-99>`). Columns tagged person/contact_pii in the context, or with PII hints, are always masked. Profiler vocabulary (null tokens, sentinels, format labels, kind names) is never masked | Cleaning rules for label columns need real values (113 category spellings); ids, names, free text and amounts don't — their shape is enough. "Label-like" extends "categorical" (≤ 50 values) so `category` (111 values in 10k rows) stays readable | Mask everything (agent can't map labels); send everything (PII and free text leave the system) |
| 2026-11-13 | Context prompt v2: business-only summary ≤ 60 words (no data-quality talk, no specific values); over-long summaries are cut at the last full sentence, or retried once if not even one sentence fits. Human and inferred contexts are stored side by side (PK run_id + source); the human one is used, the draft stays for comparison (`context --compare`). A human file may add `Domain:`, `Critical columns:` and `Tags:` lines | v1 summaries mixed in data-quality observations and were cut mid-sentence; keeping both lets us measure how good the draft is against the human version | Overwrite the draft with the human text (no comparison possible) |
| 2026-11-13 | The agent never writes SQL. It submits `SilverRules` (strict Pydantic, extra fields forbidden): cleaning steps from a fixed menu, date formats by registry id, actions from enums. `pipeline/silver/compiler.py` is the only code that writes silver SQL, and every rule value enters it through `psycopg.sql.Literal/Identifier` | The rule space is small, reviewable and testable (golden SQL file, injection test); a model can't produce a destructive or slow query; humans review YAML, not SQL | Let the agent write SQL (unbounded, hard to review, injection risk); a DSL string format (needs its own parser) |
| 2026-11-13 | `test_rule` instead of free SQL: the agent dry-runs ONE column rule on a fixed 2,000-row sample and sees before/after values, null/invalid shares and failing values | The agent gets the feedback it would want from ad-hoc SQL, through the same compiler that will build silver | A read-only SQL tool (still unbounded, and results wouldn't match the compiler's behaviour) |
| 2026-11-13 | Validator in four layers, stopping at the first failing one: schema (field paths) → semantic (sources, format ids, day/month order, step/type fit, issue references) → dry-run (compiled SQL on the sample as `pipeline_ro`, read-only transaction, rolled back, 10 s) → coverage (every high and medium issue id resolved by a citing rule or ignored with a reason). Errors block; warnings (invalid > 5%, rows with errors > 10%, a rule nulls > 30% of non-null values, confidence < 0.6 without a human question) go to the human reviewer. Feedback to the agent is ≤ 2 KB | Cheap checks first, and the agent fixes one class of problem at a time; the coverage layer is the guarantee that no high/medium issue is silently skipped; thresholds that are judgement calls are not errors | One flat list of every problem (noisy, expensive dry-runs on invalid rules); coverage as a warning (issues get dropped) |
| 2026-11-13 | Value-level lineage: every silver row keeps `bronze_id`, `<col>_raw` for columns whose type or nullness a rule can change, `_quality_flags` (per column: cleaned, null_token, sentinel:<value>, mapped, unmapped, unparseable, out_of_range, nulled_by_row_check), `_errors` and `_rejected` | Any silver value can be traced to its raw value and the fix that produced it; analysts can filter on flags instead of trusting the cleaning blindly | Row-level lineage only (bronze_id), which can't explain a single changed value |
| 2026-11-13 | Default rules (trim + remove hidden characters, type only at ≥ 99% confidence) for columns with no issues; the agent only writes rules for flagged columns, which override the defaults per column | The agent's effort and tokens go where the problems are; clean columns still get a safe, typed rule | Ask the agent for every column (cost scales with column count) |
| 2026-11-13 | Tools run as `pipeline_ro` (NOLOGIN, SELECT on bronze/meta, EXECUTE on silver helpers) via `SET LOCAL ROLE` inside a READ ONLY transaction with a 5 s timeout, and every value they return goes through one masking function (privacy policy). Outputs are capped at ~2 KB and logged in `meta.tool_calls` | Defence in depth: even a bug in generated SQL can't write; PII and free text never reach the model; the log shows what the agent looked at | A LOGIN role with a password in a migration file; trusting each tool to mask on its own |
| 2026-11-13 | Postgres date parsing is made as strict as Python's: `silver.try_ts` checks the regex, then round-trips the result through `to_char` with the same pattern (rejects month 00 → January, day 00 → 1st, year 0000 → 1 BC, which `to_timestamp` silently accepts), and is PARALLEL UNSAFE because its exception block needs subtransactions | Silver must agree with the profiler: on raw_tickets the compiled SQL reproduces the profiler's DATE_ORDER result exactly (1,866 / 5,319; 35.27% unambiguous) | Trust `to_timestamp` (silently invents dates); parse in Python (row-by-row, slow at scale) |
